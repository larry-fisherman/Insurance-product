# Web platform plan and implementation audit

Audited November 1, 2026 against commit `4733431`, the approved [web platform plan](WEB_PLATFORM_PLAN.md), canonical requirements/security/data documents, migrations, application code, tests, CI and existing local images. The pre-existing change to `web-platform-operations.md` was preserved. The original audit changed documentation only. The remediation record below tracks subsequent authorized code changes; the original findings and verification remain historical evidence.

## Verdict

**The complete plan is partially fulfilled.** The repository implements a substantial local, synthetic-only platform: independent marketing and operations applications, tenant accounts and roles, document intake and processing, evidence review, approved-package export, controlled activation/onboarding and manual subscription administration. The basic architectural direction is sound and its principal controls have executable tests.

It does **not** fulfill the plan's complete CGL acceptance, all promised application pages, managed-identity lifecycle, commercial billing, service-principal design, retention/offboarding, or hosted/customer-data release requirements. Passing the fictional example is insufficient to close those requirements. Several additional implementation defects were reproduced during this audit.

The appropriate milestone is **local synthetic platform with open functional and security findings**. Continue to enforce the existing local/test and fictional-data gates. Do not interpret this audit, the earlier implementation handoff, or a successful test count as authorization for customer documents or public deployment.

## Prioritized implementation findings

Priority is remediation order, not a claimed CVSS score. **P1** should be closed before customer-data use; **P2** needs a defined owner and acceptance before the affected feature is released. Preconditions distinguish current defects from conditional deployment risks.

### A01 — P1: retained upload storage is not bounded

**Confirmed by a disposable-database probe.** Three initialize → upload → abort cycles retained every uploaded byte and three part records while consuming **zero** open-upload slots. A preparer can repeat this pattern; expiration also removes sessions from the open count without reclaiming bytes. Finalized chunks remain alongside the finalized source, and failed transactions can leave unreferenced objects.

Relevant code: [uploads.py](../services/backend/app/uploads.py), initialization lines 92–109, part storage 144–158, finalization 179–194 and abort 197–204; [api.py](../services/backend/app/api.py), active-document packet limit 618–623. A submission's active-document limit does not bound retained versions or unfinished storage.

**Impact:** an authorized or compromised preparer can exhaust shared disk/object capacity or increase costs, affecting other agencies. No attempt to fill storage was made; the probe retained only 87 fictional bytes.

**Required change:** reserve tenant/global retained-byte and in-flight capacity transactionally; include aborted, expired, finalized-temporary and historical categories in accounting; implement a bounded, auditable orphan/temporary-part cleanup policy with grace periods and current finalization/hold checks. Preserve finalized original bytes and historical evidence. Add abort/retry/expiry/rollback/concurrency and exhausted-capacity tests. Upload/download capacity controls are consistent with [OWASP file-upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html#upload-and-download-limits).

### A02 — P1: new records carry incorrect schema and rule versions

**Confirmed by a disposable-database probe.** A new reviewed revision has `canonical_revision.schema_version = cgl-1` while its frozen JSON says `cgl-2`. New discrepancy rows have `rule_version = cgl-1`, while the active rule constant is `cgl-rules-2`.

Relevant code: [workflow.py](../services/backend/app/workflow.py), `save_revision` 777–815 and `refresh_issues` 273–304; [domain/models.py](../services/backend/app/domain/models.py), defaults at 216 and 249; [domain/cgl.py](../services/backend/app/domain/cgl.py), version constants 13–15. The reconciliation result does not supply `rule_version` to override the default.

**Impact:** the audit trail misidentifies how current results were produced; future readers/migrations cannot safely select behavior using the stored version. Exact byte hashes still protect the artifacts they identify, but do not correct false version labels.

**Required change:** write explicit, consistent versions for every new run/finding/revision/package; bind schema, pipeline, prompt, rules, requirements, template and renderer in a complete immutable version manifest. Preserve historical rows and bytes; use a documented compatibility/annotation strategy for inconsistent historical metadata rather than rewriting immutable history. Test old/current readers and version changes across generation and approval.

### A03 — P1 conditional: configuration can collapse the cookie boundary

**Confirmed configuration defect.** `Settings` accepts application `http://localhost:3000` and marketing `http://localhost:3001`. Marketing's own configuration also validates each origin independently without rejecting equal hostnames.

Relevant code: [config.py](../services/backend/app/config.py), 70–83; [marketing config](../apps/marketing/src/lib/config.ts), 1–22. Current Compose defaults use different hostnames and are protected from this specific configuration mistake.

**Impact/precondition:** if an operator puts the two services on the same hostname with different ports, app cookies can be sent to the marketing server. A compromised marketing runtime would then receive credentials that the architectural boundary intended to exclude. Cookies do not isolate ports. [RFC 6265 security considerations](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5)

**Required change:** reject equal canonical hostnames in backend and both build/runtime configurations; validate hosted HTTPS and cookie migration rules; include negative same-host and proxy/forwarding tests in startup and CI. Do not weaken host-only cookies to make a shared-host setup work.

### A04 — P2: provider authentication age is replaced with callback time

**Confirmed with a signed synthetic ID token and real session persistence.** A token whose `auth_time` was 590 seconds old was accepted; a sensitive revoke-other-sessions action still succeeded 20 seconds later. The actual authentication was then 610 seconds old, exceeding the plan's ten-minute threshold.

Relevant code: [oidc.py](../services/backend/app/oidc.py), 147–151 and 284–287; [identity.py](../services/backend/app/identity.py), `set_session` 137–156 and `require_recent` 633–641; [migration 0007](../services/backend/migrations/versions/0007_platform.py), authenticated-at default 60–64.

**Impact/precondition:** in OIDC mode the sensitive-action window can approach twenty minutes from the provider authentication. This does not bypass signatures, nonce, MFA or membership checks. Current default local-password mode is unaffected by this specific error.

**Required change:** persist the validated provider `auth_time`; validate age against the requested authentication assurance/max-age contract, with a documented clock-skew allowance; preserve the original intent/version through reauthentication without automatic resubmission. Add boundary-time, provider-revocation, key-rotation and concurrent-callback tests. [OIDC ID-token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)

### A05 — P2: isolated parser transport discards security error codes

**Confirmed with a bounded mocked transport.** A parser response `422 {"error":"ACTIVE_PDF_CONTENT"}` becomes `DocumentError("PARSE_FAILED")` in the worker. The same loss applies to useful password/resource/format failures.

Relevant code: [parser_service.py](../services/backend/app/parser_service.py), 85–86; [parser_client.py](../services/backend/app/parser_client.py), 43–47; [api.py](../services/backend/app/api.py), unsafe-document retry guard 815–818.

**Impact:** the unsafe-document retry guard cannot recognize a parser-rejected active PDF in the isolated full stack. The file remains quarantined; no scan or active-content execution bypass was demonstrated. Operators also lose actionable diagnostics, and repeated manual retries consume capacity.

**Required change:** validate a small closed error-response schema with an allowlist of codes and preserve their retry policy. Keep unavailable, busy, hostile, unreadable and resource-limited states distinct. Test these responses over the actual isolated transport, not only the native parser fallback.

### A06 — P2: extraction provider responses are loaded without a byte bound

**Confirmed by code inspection; no oversized external response was sent.** [documents.py](../services/backend/app/documents.py), 948–962, performs a non-streaming `post` and `response.json()` before validating the result. The input-character limit, output schema and OpenAI token request do not impose a transport-byte bound on an arbitrary gateway response.

**Impact/precondition:** a misbehaving or compromised configured provider can exhaust worker memory with an oversized body before validation. Browser documents cannot choose the provider endpoint, which limits direct exploitability.

**Required change:** stream and cap bytes before JSON decoding, bound JSON structure and accepted output, constrain egress to approved destinations, and enforce actual per-tenant/provider usage budgets. Test large bodies, compression expansion, slow responses and invalid output. No paid provider call was made during this audit.

### A07 — P2: abuse controls and proxy trust are incomplete

**Confirmed by code inspection and routing probes.** Inquiry intake uses one global 30-record/minute budget; a single bot can consume it and prevent legitimate inquiries. The counter query has no `created_at` index or retention job. Identity throttling keys only `request.client.host` plus operation, with no account/user/tenant dimension. The Next.js proxy and API need a documented trusted-client-address contract before hosted use; otherwise all proxied users can share a limiter bucket, or unsafe forwarding trust can allow spoofing.

Relevant code: [inquiries.py](../services/backend/app/inquiries.py), 46–54 and 93–125; [identity.py](../services/backend/app/identity.py), 129–134; [limiting.py](../services/backend/app/limiting.py); [API Dockerfile](../infra/local/api.Dockerfile), 24; [app proxy](../apps/web/src/proxy.ts), 3–5. A correct Host plus spoofed `X-Forwarded-Host` was accepted with HTTP 200. No redirect or authorization exploit resulted in the probe; this is incomplete ingress acceptance, not proof of a host-header exploit.

**Required change:** trusted-edge header stripping/replacement and explicit trusted-proxy configuration; layered IP/account/agency/action limits and expensive-operation reservations; public abuse/verification controls appropriate to a released inquiry form; indexed, privacy-minimized, expiring counters. Preserve fail-closed limiter behavior on Redis failure. Add repeated-inquiry, distributed-client and spoofed-forwarding tests.

### A08 — P2: promised pages and route semantics are incomplete

**Confirmed by route and component inspection.** `/renewals` and `/approvals` are not in the operations route allowlist. `/settings/security` and `/settings/data` fall through to the team component rather than their promised functions. `/insureds/new` is treated as an insured ID. Several planned submission paths have changed: processing is embedded in documents, reconciliation in review, package uses `/packages`, and history uses `/audit`. Unknown submission tabs render no tab content rather than a meaningful 404. The documented local deviations cover some combined screens, but do not implement absent queues/settings.

Relevant code: [operations route](<../apps/web/src/app/(operations)/[...path]/page.tsx>), 10–23; [shell](../apps/web/src/components/workspace/shell.tsx), 50–80; [submission tabs](../apps/web/src/components/workspace/submission.tsx), 902 onward; planned routes in [the plan](WEB_PLATFORM_PLAN.md#application-page-structure).

**Required change:** implement renewal and approval queues, define the intended agency security/data settings, complete the saved onboarding checklist and role-grant reasons, and either implement or explicitly redirect all approved route aliases. Reject invalid subroutes. Add route/permission tests and usable bounded/cursor navigation for administrative histories.

### A09 — P2: dependency and release controls have open findings

**Fresh advisory result:** npm reports 18 moderate affected package entries caused by **one** `minimatch` advisory, [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249). Locked affected instances are marked development dependencies, including versions 3.1.5, 5.1.9 and 10.2.6. This is development/build availability exposure, not evidence of eighteen distinct vulnerabilities or a demonstrated production application exploit. The advisory lists 11.0.1 as patched.

Python runtime dependency auditing examined 61 locked packages and returned no known advisories or skipped packages. This does not assess OS/native libraries or prove absence of unknown vulnerabilities. Docker Scout is installed but its image-CVE check could not complete because it requires login. No container CVE clearance is claimed.

Relevant code: [package lock](../package-lock.json), [Python lock](../services/backend/uv.lock), [CI](../.github/workflows/ci.yml), [Dockerfiles](../infra/local/). CI has dependency updates and functional checks but no vulnerability/SBOM/secret-scanning/release-attestation gates. Its browser command does not enable the ordinary ClamAV case or run the runtime boundary verifier.

**Required change:** update compatible upstream dependency chains and regenerate/test the lockfile; do not apply the audit tool's suggested forced ESLint downgrade blindly. Add continuous package/container/secret scans, image-digest and release provenance, public artifact checks, scanner-enabled browser acceptance and boundary tests. Triage findings by actual runtime reachability. Provide an approved scanner execution path that does not depend on an interactive developer login.

### A10 — P2: invitation secrets remain in the URL until acceptance

**Confirmed by code inspection.** Activation reads/removes a fragment immediately, but invitation acceptance reads fragment or legacy query tokens only when submitting. There is no short-lived browser-bound invitation intent exchange.

Relevant code: [invitation acceptance](../apps/web/src/components/workspace/settings.tsx), 286–314; [activation](../apps/web/src/components/workspace/platform.tsx), 325–335. New invitations use fragments and app responses use `Referrer-Policy: no-referrer`, which reduce exposure; legacy query tokens still reach ingress. Raw secrets were not printed or included in this report.

**Required change:** capture an invitation secret on a minimal page, exchange for a browser-bound expiring intent and remove it from history before ordinary navigation; redact legacy query tokens in every ingress/telemetry layer. Opening a link must not consume the invitation. Exercise login in another tab, reload, replay and expiration.

### A11 — P2: fresh browser acceptance is unstable and its status assertion races export

The default scanner-enabled four-case audit run produced **three passes and one failure**. Ordinary scanned upload, mobile login and marketing inquiry passed. Broker review reached approval, then exceeded the global 120-second budget while reading exported PDF bytes; teardown disposed the response. That is not evidence that exported bytes were wrong. It is also not a passing end-to-end audit run.

Separately, [workflow.spec.ts](../tests/e2e/workflow.spec.ts), 113–118, asserts that the heading still says `approved` after the export request. [api.py](../services/backend/app/api.py), 1096–1097, changes current submissions to `exported`. The assertion therefore depends on polling latency and should distinguish pre-export approval from post-export state.

**Required change:** measure stage timings, test approved status before requesting export, then verify bytes, recorded export and the exported state. Use stage-appropriate, justified budgets and record latency regressions rather than merely increasing the global timeout. Add ordinary identity/onboarding/billing/role-specific browser flows and the adverse cases reproduced by this audit.

## Additional release-critical work

These are recognized plan gaps, not newly demonstrated exploits:

1. **Identity and least privilege:** connect an approved test identity provider and accept its MFA/authentication-time/recovery/key-rotation/disablement/logout contract. Implement provider lifecycle reconciliation and explicit processing service principals with tenant/job grants, narrow dispatch visibility, initiating/executing actor attribution and authorization-change checkpoint tests. Current workers/scheduler inherit both operations database connections and the private-file volume. They are not the planned restricted principals.
2. **Parser and source preview boundary:** independently test hostile PDF/XLSX/OCR inputs, egress, filesystem/process isolation and resource saturation. The child shares a persistent container/user and timeout handling kills the immediate subprocess rather than a dedicated per-job process group. ZIP inspection still runs in credentialled intake/worker code before isolated parsing. Raw original PDFs are used for inline evidence; active-object checks and sandbox response headers exist, but are not acceptance of the plan's safe rendered-preview design. Validate raster/text or separately isolated previews and reliable PDF geometry.
3. **CGL domain completion:** obtain licensed reviewer decisions for entity/operation relationships, gross/net/component exposures and rating denominators, aggregate/retention applicability, form editions, claims-made limitations, claim component/recovery/valuation semantics and approved requirements. Validate representative native/scanned/mixed PDFs and complex workbooks with independently labeled held-out cases. Test numeric/context/evidence errors and unsupported package assertions; generated label-based regression scores do not establish insurance accuracy.
4. **Retention and customer administration:** implement category retention, holds, tenant offboarding/data return/deletion, derivative/vendor erasure, backup expiry and restored-backup enforcement. Add operator workflows with separate authority and attributable access. Ordinary runtime roles should not gain blanket deletion powers.
5. **Actual hosted controls and recovery:** accept DNS/TLS/ingress, database/queue TLS, private storage/KMS/versioning, workload identities, secret rotation and egress in the actual environment. Restore exact object versions and approval hashes into isolated infrastructure; include inquiries and resumable transfer state. Define/test RPO, RTO, SLOs, owned alerts and incidents.
6. **Commercial integrations:** choose approved pricing/billable units, email and payment vendors. Implement hosted checkout/portal and signed, deduplicated, reconciled billing events in test mode before charging. Reconcile retries against logical billable units; measure actual provider and infrastructure usage/cost. Obtain approved legal/privacy/security contact content and pilot scope.

Consider additional insurance lines, AMS/carrier sending, client portals, mandatory two-person approval or further platform abstractions only after the first-release CGL path and agreed release controls pass. These are optional scope decisions, not substitutes for the work above.

## Recommended next delivery sequence

1. **Close reproduced defects:** A01–A06, then dependency/CI and ingress controls. Acceptance includes negative tests for same-host configuration, exact provider auth age, retained-byte quotas/cleanup, preserved parser error policy and coherent immutable version metadata.
2. **Make first-release workflows complete and stable:** A08/A10/A11; finish onboarding and role-specific screens; add renewal/approval queues and explicit route aliases; complete adverse, race, retry, crash and deprovisioning tests. Keep the exact approval/export and forced-RLS invariants.
3. **Obtain domain acceptance while completing operational controls:** representative held-out CGL evaluation, approved requirements/templates, durable page outcomes, service principals, retention/holds/data return and full restore exercises. This work can proceed in parallel with external identity/vendor choices.
4. **Prepare an approved hosted test environment:** configure accepted identity/cloud/storage/email/payment test accounts and independently assess the deployed controls. Do not remove the current release gate merely to run it elsewhere.
5. **Authorize a limited customer-data pilot only after recorded gates pass:** use [pilot readiness](pilot-readiness.md), with explicit scope, support, quality/cost/capacity evidence and customer authority. Manual pilot billing remains possible if explicitly agreed. Broader commercial launch is a later gate.
