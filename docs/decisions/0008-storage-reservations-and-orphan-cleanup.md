# ADR 0008: PostgreSQL storage reservations and reservation-backed orphan cleanup

Date: November 2, 2026. Status: accepted for local synthetic A01 remediation.

## Context

[ADR 0006](0006-local-storage-capacity.md) admits filesystem writes by scanning retained bytes under one host-local `flock`. That cannot coordinate several hosts or an S3 client, and the scan is O(retained entries) on every write. [ADR 0007](0007-temporary-upload-cleanup.md) can reclaim expired parts of known upload sessions, but objects written without a committed business row (a rolled-back `store_document`, a package render whose job lease was lost, a part whose request rolled back outside a known session) have no durable write intent, so nothing can safely say who wrote them or whether a writer is still in flight.

## Decisions

**The ledger is the admission authority for every adapter.** Before any `Store.put`, the writer commits a tenant-scoped `storage_reservation` row (purpose `upload_part`, `document` or `artifact`; owner, slot, server-generated key, exact byte count, SHA-256, request hash and expiry). Reservation and charge happen in one short transaction, separate from the business transaction, through a `SECURITY DEFINER` function that applies one conditional `UPDATE ... WHERE used + n <= limit` to the tenant row and one to the global row. If either fails, nothing is inserted and the writer receives `STORAGE_CAPACITY_REACHED` (507). An uninitialized ledger returns `STORAGE_QUOTA_UNAVAILABLE` (503). The same function binds retries: an unexpired `reserved` row with the same tenant, purpose, owner, slot and request hash is reused, including its key, and a different hash on that live slot conflicts. A retried part therefore cannot double-charge or silently rebind to different bytes. A reused key whose object already holds the identical bytes counts as written. Reservations use a dedicated small connection pool, so they never wait for a business connection. `storage_reservation` deliberately has no tenant or membership foreign key: an FK check would take a key-share lock on the tenant row, which the caller's own business transaction already holds `FOR UPDATE`, and the separate reservation transaction would wait on its own request. Forced RLS and the definer bind the tenant and validate the creating member.

**Linking is a reservation-row update only.** The business transaction locks its reservation `FOR UPDATE`, requires `state='reserved'`, an unexpired TTL and the expected key, then sets `committed`. It does not touch usage counters, so a business transaction never holds the tenant or global counter row. Counter rows are locked only by short reserve, reconcile and cleanup-completion statements. Consequently `storage_usage.reserved_bytes` is the charge for every unreleased reservation in any state, and `committed_bytes` is the pre-ledger baseline established by the seed/reconcile command. The tenant's charge is their sum. A guard trigger permits only forward transitions (`reserved → committed | cleanup_planned | released`, `committed → released`, `cleanup_planned → released`), keeps identity, key, size and hash immutable, refuses linking an expired reservation, and allows `released` only from the definer functions.

**Charges are released only by verified deletion or a verified-absent expired reservation.** Release happens only in the completion functions for a cleanup intent, after the application has validated and unlinked the whole batch under the storage lock. Rolled-back, quarantined, failed, excluded, aborted and orphaned bytes stay charged. Documents and package artifacts can never be released once committed; the definer refuses any reservation whose key a `document_version` or `package_artifact` row references.

**Global accounting goes through minimal definer functions.** The global row (`storage_global_usage`) and limits (`storage_limit`) have forced RLS and no runtime grant. Runtime can `SELECT` its own `storage_usage` row only. Every definer function uses `SET search_path=pg_catalog,app` and `REVOKE ALL ... FROM PUBLIC`. Only `reserve_storage`, `reconcile_storage`, `release_upload_cleanup` and `release_object_cleanup` receive an explicit `GRANT EXECUTE` to `cgl_runtime`; `release_storage` and `storage_ready` are internal. Each derives the tenant from `app.current_tenant_id()` and requires `app.active_member(...)`; no function accepts a tenant argument, key list or path. Threat model: a runtime caller in tenant A must not read or change tenant B's usage, see the global total, or lower any counter outside a real cleanup. The functions return only closed outcome codes and the caller's own reservation fields. The cross-tenant reads they perform are the global row, the limit row and an `EXISTS` readiness check over unseeded tenants. A compromised runtime process could still call a completion function for its own tenant's real cleanup intent; that is the same trust already given to the process that performs the unlink. Migration/admin credentials are never used on request, worker or CLI paths.

**Limits live in a migration-managed table.** `storage_limit` is a singleton holding the per-tenant byte limit (2 GiB), the global byte limit (20 GiB) and the global entry limit (100,000), the ADR 0006 defaults. API and worker processes cannot diverge. The former `CGL_STORAGE_*_LIMIT` settings are removed. Changing a limit is a reviewed migration (or a migrator-owned operation in a disposable test database).

**Quota scope.** There is one tenant budget plus the global limit. It covers originals, upload parts, derived artifacts and orphans. There is no per-submission quota; the existing `PACKET_LIMIT` is unchanged. Each reservation charges one entry. The seed counts files and directories under `tenants/{id}/` exactly as ADR 0006 did, so directory overhead is charged for pre-ledger history but not for new writes. That is a documented approximation, not filesystem overhead accounting.

**Fail closed until seeded.** Migration `0010_storage` creates `initialized=false` usage rows for existing tenants. The tenant-insert trigger creates `initialized=true` rows for new tenants. Reservation is unavailable for a tenant until its row is initialized, and for every tenant while any active tenant with an active member remains unseeded, because the global total would otherwise omit its bytes. Tenants that cannot act (no active member) are reported by the seed command, and their bytes are outside the global total until they become seedable and are seeded. `make full-up` runs the seed in the API image against the private volume before starting services.

**Seed and reconciliation (operator CLI).** `python -m app.storage_admin reconcile` lists tenants through the identity pool (the `agency_actors` pattern), opens one runtime tenant session per tenant, and, while holding the storage `flock`, scans that tenant's directory and calls `app.reconcile_storage`. The first run sets the baseline and `initialized`. Later runs raise the baseline when actual bytes or entries exceed the ledger, never lower it, and record signed drift in `storage_sweep`. Holding the `flock` across the scan and the counter update keeps a concurrent cleanup from making the scan look larger than the ledger. Nothing that holds a counter row waits for the `flock`.

**Lock order.** Database upload/business row → cleanup intent row → reservation rows → storage `flock` → counter rows. Runtime cannot row-lock the immutable `object_cleanup` intent (it has no `UPDATE` grant), so orphan execution serializes on its planned reservation rows and the completion function locks the intent last. Reserve takes the tenant counter, then the global counter, and only reads reservations. Release takes reservation, then tenant counter, then global counter. The reconcile command is the one place that takes the `flock` before a counter row.

**Versioned policy constants, not settings.** Policy `storage-orphan-cleanup-1` uses a 1-hour reservation TTL, a 5-minute writer safety margin and a 24-hour orphan grace after expiry, well above the 12-minute job lease and 600-second hard task limit. These constants sit beside `POLICY_VERSION` in `app/upload_cleanup.py`. A writer refuses to write, inside the storage lock, once its reservation is within the margin of expiry. `link()` refuses an expired reservation.

**Reservation-backed orphan cleanup.** This is an explicit two-request admin plan/execute flow, as in ADR 0007. It requires `retention.manage`, recent authentication and request-hash idempotency. A candidate is `state='reserved'`, past expiry plus grace, and its key is referenced by no `document_version`, `package_artifact` or `upload_part` row. Planning selects at most 100 candidates with `FOR UPDATE SKIP LOCKED`, marks them `cleanup_planned` (so a late `link()` fails instead of racing), and inventories each object with bounded, symlink-refusing, single-link, regular-file inspection. It records presence, size, hash and modification time in an immutable `object_cleanup` intent and audit event. Nothing is deleted. Execution re-locks the intent and reservations, rechecks current authority, grace and references, and validates the whole batch under the storage lock before unlinking. It then completes the intent and releases the reservations in one definer call, and records an audit event. A reservation whose object was never written (crash before write) completes as `already_absent` with no bytes deleted. Replay tolerates objects that are already absent and releases exactly once, because completion and release are one statement guarded by `completed_at IS NULL`.

**ADR 0007 release rule.** Completing an upload cleanup intent is now one definer call. It releases each planned part that has a reservation by that reservation (once, whatever its state), and lowers the pre-ledger baseline by the manifest bytes of planned parts with no reservation, clamped at zero. Execution validates and unlinks the whole manifest before that call, so every planned object is absent when it runs. A held upload never reaches it.

**Report-only scheduler sweep.** The Celery beat task `cgl.storage_sweep` uses the per-tenant scoped-session pattern. It claims a per-tenant `storage_sweep` lease with `FOR UPDATE SKIP LOCKED`, `lease_until` and `attempt`. It counts orphan candidates, expired-absent reservations, legacy unreserved files (walking only `tenants/{id}/`) and ledger drift, and writes counts only, with `origin='scheduler'` and no member attribution. A stale attempt cannot overwrite a newer report. Unknown tenant directories are logged as an anomaly count and never opened. The scheduler never deletes. `storage_sweep_mode` accepts only `report`. The sweep borrows an arbitrary active member for RLS scope, the same known limitation as job dispatch; production service principals remain open.

**Legacy pre-ledger orphans are report-only permanently** for this work. A file with no reservation confers no authority to delete. Any future deletion path for such files needs its own reviewed, attested design.

**Visibility is operator-CLI only.** `python -m app.storage_admin report` prints per-tenant usage and the latest sweep counts (no keys or paths). Agency-admin read endpoints or UI are future work.

**The S3 gate stays closed.** The ledger is adapter-neutral by design, but S3 still returns `STORAGE_QUOTA_UNAVAILABLE` before any charge or provider call. Conditional S3 writes and the gate remain closed until a local S3-compatible service and its release evidence exist.

## Consequences and limits

All three write sites (`store_document`, `put_part`, package artifacts) reserve → write → link. `FileStore.put` keeps exclusive create and the `flock`, but no longer scans. The scan survives only for seeding, reconciliation and the sweep. Counters can be higher than retained bytes (expired-absent reservations, released-later deletions, directory overhead in the baseline) and are never silently lowered. Physical disk monitoring, filesystem overhead, category retention, tenant-wide holds, offboarding/erasure, backup expiry, restored-backup enforcement and provider/derivative erasure remain open. No customer-data, public-deployment or S3 gate changes.

## Verification

Disposable-database regression tests cover exact tenant/global/entry boundaries, multi-process admission at the boundary for parts and artifacts, concurrent API part uploads, retry reuse and different-hash conflict, uninitialized and globally unready ledgers failing closed, runtime privilege limits and cross-tenant invisibility, rollback and crash-mid-write charges, lease-lost renders, link-once redelivery, over-quota renders failing without retry, retained excluded/superseded/failed/quarantined documents and artifacts of every package status never becoming candidates, late link after planning, changed bytes, symlinks, late writes, revoked permission, idempotency conflict, crash/replay releasing exactly once, never-written reservations, the writer margin, seed/reconcile idempotency and drift, ADR 0007 release (including holds and pre-ledger parts), and sweep lease/stale-attempt/repeat-delivery/tenant-directory confinement. Fresh results are recorded in the [platform audit](../WEB_PLATFORM_AUDIT.md).
