# ADR 0008: PostgreSQL storage reservations and reservation-backed orphan cleanup

Date: November 2, 2026, revised November 3, 2026 after review. Status: accepted for local synthetic A01 remediation.

## Context

[ADR 0006](0006-local-storage-capacity.md) admits filesystem writes by scanning retained bytes under one host-local `flock`. That cannot coordinate several hosts or an S3 client, and the scan is O(retained entries) on every write. [ADR 0007](0007-temporary-upload-cleanup.md) can reclaim expired parts of known upload sessions, but objects written without a committed business row (a rolled-back `store_document`, a package render whose job lease was lost, a part whose request rolled back outside a known session) have no durable write intent, so nothing can safely say who wrote them or whether a writer is still in flight.

## Decisions

**The ledger is the admission authority for every adapter.** Before any `Store.put`, the writer commits a tenant-scoped `storage_reservation` row (purpose `upload_part`, `document` or `artifact`; owner, slot, server-generated key, exact byte count, SHA-256, request hash and expiry). Reservation and charge happen in one short transaction, separate from the business transaction, through a `SECURITY DEFINER` function that applies one conditional `UPDATE ... WHERE used + n <= limit` to the tenant row and one to the global row. If either fails, nothing is inserted and the writer receives `STORAGE_CAPACITY_REACHED` (507). An uninitialized ledger returns `STORAGE_QUOTA_UNAVAILABLE` (503). The same function binds retries: a `reserved` row with the same tenant, purpose, owner, slot and request hash is reused, including its key, and its TTL is renewed if it has lapsed; a different hash on a live slot conflicts, and a stable key already planned, released or linked is never rebound. A retried write therefore cannot double-charge or silently rebind to different bytes. A reused key whose object already holds the identical bytes counts as written. Owners are stable across a rollback: a part's owner is its upload, a finalized document's ID derives from its upload, and a directly uploaded document's ID derives from its `Idempotency-Key`. Package artifacts reserve per attempt and format, so a lease-lost attempt deliberately stays a charged orphan. Reservations use a dedicated small connection pool, so they never wait for a business connection.

**Foreign keys are restored (migration `0011_storage_narrow`).** `storage_reservation` references `tenant(id)` and `membership(tenant_id, id)`, so migrator and maintenance writes are bound and a later tenant or membership delete cannot leave a dangling reference. Migration `0010_storage` omitted them because `require_capacity` held the tenant row `FOR UPDATE`, which conflicts with a foreign key check's `FOR KEY SHARE`, so the reservation's separate connection would wait on its own request. `require_capacity` now takes `FOR NO KEY UPDATE`, which still serializes capacity decisions (it conflicts with itself and with `FOR UPDATE`) but admits `FOR KEY SHARE`. The membership key only ever locks a membership row, which no reserving transaction holds exclusively; member administration does, briefly, in its own request. `test_foreign_keys_bind_reservations_without_waiting_on_the_capacity_lock` shows both lock modes. `owner_id` and `release_ref` stay unconstrained because they point at different tables by purpose. The definer also requires `created_by` to be the caller's own active membership.

**Linking is a reservation-row update only.** The business transaction locks its reservation `FOR UPDATE`, requires `state='reserved'`, an unexpired TTL and the expected key, then sets `committed`. It does not touch usage counters, so linking never holds the tenant or global counter row. Reserve and reconcile hold counter rows for one short transaction. Cleanup completion is different: its definer runs inside the cleanup request's transaction, so it holds both counter rows until that request commits in its teardown. Consequently `storage_usage.reserved_bytes` is the charge for every unreleased reservation in any state, and `committed_bytes` is the pre-ledger baseline established by the seed/reconcile command. The tenant's charge is their sum. A guard trigger permits only forward transitions (`reserved → committed | cleanup_planned | released`, `committed → released`, `cleanup_planned → released`), keeps identity, key, size and hash immutable, refuses linking an expired reservation, and allows `cleanup_planned` and `released` only from the definer functions.

**Lock waits are bounded and stay off the event loop.** Every storage definer carries `SET lock_timeout='5s'`, and `link()` and the whole part-upload request bound their waits the same way. A wait that hits the bound, or a deadlock, returns `STORAGE_QUOTA_UNAVAILABLE` (503) with no charge, and replay remains safe. `put_part` is a plain `def` route, so FastAPI runs it and its request teardown in the threadpool. Only the bounded, authenticated body read runs on the event loop, before any database lock is taken. Before this, a part upload waiting on the global counter blocked the event loop, and so could block the teardown of the very request holding that row, hanging a single-process API for every tenant. `test_part_waiting_on_a_counter_row_cannot_stall_the_shared_event_loop` shares one event loop to prove this.

**Charges are released only by verified deletion or a verified-absent expired reservation.** Release happens only in the completion functions for a cleanup intent, after the application has validated and unlinked the whole batch under the storage lock. Rolled-back, quarantined, failed, excluded, aborted and orphaned bytes stay charged. Documents and package artifacts can never be released once committed; the definer refuses any reservation whose key a `document_version` or `package_artifact` row references.

**Upload parts are never touched by orphan cleanup.** `candidates()` excludes `purpose='upload_part'`, the planning definer refuses a part, and execution refuses a part listed by any plan from before migration `0011_storage_narrow`. ADR 0007's plan/execute flow, which respects preservation holds, is the only path that deletes upload parts. A rolled-back part with no upload session stays on disk and is only reported, as `unlinked_upload_parts` in the sweep and `make storage-report`. Its bytes stay charged.

**Global accounting goes through minimal definer functions.** The global row (`storage_global_usage`) and limits (`storage_limit`) have forced RLS and no runtime grant. Runtime can `SELECT` its own `storage_usage` row only. Every definer function uses `SET search_path=pg_catalog,app` and `REVOKE ALL ... FROM PUBLIC`. `reserve_storage`, `plan_upload_cleanup`, `plan_object_cleanup`, `release_upload_cleanup` and `release_object_cleanup` are granted to `cgl_runtime`; `reconcile_storage` is granted only to `cgl_storage_operator`; `release_storage` and `storage_ready` are internal. Each derives the tenant from `app.current_tenant_id()` and requires `app.active_member(...)`; no function accepts a tenant argument. `reserve_storage` takes a server-generated key that it binds to the session's tenant and purpose, and the planning functions take a manifest but decide eligibility from database rows. Threat model: a runtime caller in tenant A must not read or change tenant B's usage, see the global total, or raise or lower counters except through a reservation or a real cleanup. The functions return only closed outcome codes and the caller's own reservation fields. The cross-tenant reads they perform are the global row, the limit row and an `EXISTS` readiness check over unseeded tenants. Migration/admin credentials are never used on request, worker or CLI paths.

**Measurements come only from the operator role.** `reconcile_storage` accepts a measured byte and entry count that PostgreSQL cannot verify, and one forged call could fill the shared global budget and deny every tenant. It is therefore granted only to `cgl_storage_operator`, a login role that can reach this one function and no table. Its credential lives in `services/backend/.env.storage-operator`, which is loaded only by the one-shot `storage-admin` Compose service; API, worker and scheduler containers load `.env.app` and never receive it. A tenant-scoped runtime session cannot call the function at all.

**Cleanup intents come only from the planning definers.** Runtime has no `INSERT` on `upload_cleanup` or `object_cleanup`, and the guard trigger refuses a direct move to `cleanup_planned`. `plan_object_cleanup` plans only unlinked, unreferenced document or artifact reservations past expiry plus grace. `plan_upload_cleanup` plans only an expired, unheld upload past grace, with no retained reference to the listed names. Completion rechecks the hold and expiry, and every byte lowered comes from a reservation row or a reconcile-recorded legacy part, never from a manifest.

**Remaining trust in the runtime role, stated plainly.** PostgreSQL cannot see the filesystem, so it cannot verify an unlink. A compromised runtime process holding an administrator's user ID could plan and complete a cleanup for genuinely eligible objects without unlinking them. That lowers only those objects' real charge, once. The bytes then stay on disk uncharged until the next reconcile raises them back, and the sweep reports the drift meanwhile. It cannot lower a linked document or artifact, a live reservation, a held upload or a live upload, and cannot lower by a fabricated amount. Closing this fully would mean moving unlinks into a separately privileged process, which is future work for production service principals.

**Limits live in a migration-managed table.** `storage_limit` is a singleton holding the per-tenant byte limit (2 GiB), the global byte limit (20 GiB) and the global entry limit (100,000), the ADR 0006 defaults. API and worker processes cannot diverge. The former `CGL_STORAGE_*_LIMIT` settings are removed. Changing a limit is a reviewed migration (or a migrator-owned operation in a disposable test database).

**Quota scope.** There is one tenant budget plus the global limit. It covers originals, upload parts, derived artifacts and orphans. There is no per-submission quota; the existing `PACKET_LIMIT` is unchanged. Entries count files and directories under `tenants/{id}/` exactly as ADR 0006 did, for both the seed and new writes, so the entry limit bounds directories as well as objects. A reservation charges one entry for its object, one for its directory unless a live reservation of the same owner already created it, and one each for the tenant and category directories the first time (`storage_usage.charged_directories`). It records that charge in `entry_charge` and returns exactly that on release. The ledger therefore matches the scan, and reconcile no longer raises entries for a tenant's ordinary writes. Limits: a release of one part while its siblings remain returns the shared directory's entry early, and rows from before migration `0011_storage_narrow` keep the single entry they were charged, so entries raised by earlier reconcile runs stay in the baseline. Both are reported as drift. This is not filesystem overhead accounting.

**Fail closed until seeded.** Migration `0010_storage` creates `initialized=false` usage rows for existing tenants. The tenant-insert trigger creates `initialized=true` rows for new tenants. Reservation is unavailable for a tenant until its row is initialized, and for every tenant while any active tenant with an active member remains unseeded, because the global total would otherwise omit its bytes. Tenants that cannot act (no active member) are reported by the seed command, and their bytes are outside the global total until they become seedable and are seeded. `make full-up` runs the seed in the API image against the private volume before starting services.

**Seed and reconciliation (operator CLI).** `python -m app.storage_admin reconcile` lists tenants through the identity pool (the `agency_actors` pattern), opens one runtime tenant session per tenant, and, while holding the storage `flock`, scans that tenant's directory and calls `app.reconcile_storage`. The first run sets the baseline and `initialized`. Later runs raise the baseline when actual bytes or entries exceed the ledger, never lower it, and record signed drift in `storage_sweep`. It runs the definer as `cgl_storage_operator` and writes the report row through the runtime role. Each run also records every unreserved upload part it measures in `storage_legacy_part`. Holding the `flock` across the scan and the counter update keeps a concurrent cleanup from making the scan look larger than the ledger. Nothing that holds a counter row waits for the `flock`.

**Lock order.** Upload cleanup execution: upload row → intent row → storage `flock` (released) → reservation rows → tenant counter → global counter. Orphan execution: reservation rows → storage `flock` (released) → intent row → tenant counter → global counter. Runtime cannot row-lock the immutable `object_cleanup` intent (it has no `UPDATE` grant), so orphan execution serializes on its planned reservation rows and only the completion function locks the intent. Both completion functions lock all of a plan's reservation rows in ID order before any counter row. Reserve takes the logical-slot advisory lock → that slot's reservation row → tenant counter → global counter. The reconcile command is the one place that takes the `flock` before a counter row, and its wait for those rows is bounded.

**Versioned policy constants, not settings.** Policy `storage-orphan-cleanup-1` uses a 1-hour reservation TTL, a 5-minute writer safety margin and a 24-hour orphan grace after expiry, well above the 12-minute job lease and 600-second hard task limit. These constants sit beside `POLICY_VERSION` in `app/upload_cleanup.py`. A writer refuses to write, inside the storage lock, once its reservation is within the margin of expiry. `link()` refuses an expired reservation.

**Reservation-backed orphan cleanup.** This is an explicit two-request admin plan/execute flow, as in ADR 0007. It requires `retention.manage`, recent authentication and request-hash idempotency. A candidate is a document or artifact reservation with `state='reserved'`, past expiry plus grace, whose key is referenced by no `document_version`, `package_artifact` or `upload_part` row. Planning selects at most 100 candidates with `FOR UPDATE SKIP LOCKED` and inventories each object with bounded, symlink-refusing, single-link, regular-file inspection. An unsafe object stays `reserved`, untouched and charged, and is left out so it cannot block the rest of the tenant's orphans; the plan fails with `ORPHAN_CLEANUP_UNSAFE` only when nothing safe remains. `plan_object_cleanup` then marks the rest `cleanup_planned` (so a late `link()` fails instead of racing) and records presence, size, hash and modification time in an immutable `object_cleanup` intent, with an audit event. Nothing is deleted. Execution re-locks the reservations, rechecks current authority, grace and references, and validates the whole batch under the storage lock before unlinking. It then completes the intent and releases the reservations in one definer call, and records an audit event. A reservation whose object was never written (crash before write) completes as `already_absent` with no bytes deleted. Replay tolerates objects that are already absent and releases exactly once, because completion and release are one statement guarded by `completed_at IS NULL`.

**ADR 0007 release rule.** Completing an upload cleanup intent is now one definer call. It releases each planned part that has a reservation by that reservation (once, whatever its state). A planned part with no reservation lowers the pre-ledger baseline only by the size reconcile measured for it in `storage_legacy_part`, once per object and clamped at zero. Separate plans listing one part therefore cannot lower its bytes twice, a part reconcile never measured lowers nothing, and manifest byte counts are never trusted. Such a part simply stays charged in the baseline if it was charged at all. Execution validates and unlinks the whole manifest before that call, so every planned object is absent when it runs. The definer refuses a held upload as well as the API.

**Report-only scheduler sweep.** The Celery beat task `cgl.storage_sweep` uses the per-tenant scoped-session pattern. It claims a per-tenant `storage_sweep` lease with `FOR UPDATE SKIP LOCKED`, `lease_until` and `attempt`. It counts orphan candidates, expired-absent reservations, unlinked upload parts, reservations stuck in `cleanup_planned`, legacy unreserved files (walking only `tenants/{id}/`) and ledger drift, and writes counts only, with `origin='scheduler'` and no member attribution. A stale attempt cannot overwrite a newer report. Unknown tenant directories are logged as an anomaly count and never opened. The scheduler never deletes. `storage_sweep_mode` accepts only `report`. The sweep borrows an arbitrary active member for RLS scope, the same known limitation as job dispatch; production service principals remain open.

**Legacy pre-ledger orphans are report-only permanently** for this work. A file with no reservation confers no authority to delete. Any future deletion path for such files needs its own reviewed, attested design.

**Visibility is operator-CLI only.** `python -m app.storage_admin report` prints per-tenant usage, the latest sweep counts, the count of `cleanup_planned` reservations and up to 20 unfinished orphan plan IDs (no keys or paths). A client that lost its plan ID and idempotency key can finish the plan with the listed ID. Agency-admin read endpoints or UI are future work. There is no way to abandon a plan: one stuck on `ORPHAN_CLEANUP_UNSAFE` stays pending and its charge stays, until its object is investigated.

**The S3 gate stays closed.** The ledger is adapter-neutral by design, but S3 still returns `STORAGE_QUOTA_UNAVAILABLE` before any charge or provider call. Conditional S3 writes and the gate remain closed until a local S3-compatible service and its release evidence exist.

## Consequences and limits

All three write sites (`store_document`, `put_part`, package artifacts) reserve → write → link. `FileStore.put` keeps exclusive create and the `flock`, and refuses a symlinked or non-directory ancestor under the private root (the old admission scan's symlink check), but no longer scans. The scan survives only for seeding, reconciliation and the sweep. Applying migration `0011_storage_narrow` to an existing volume requires `make app-config` and `make app-roles` first, which `make full-up` runs in that order; the migration stops with a clear error if the operator role is missing. Counters can be higher than retained bytes (expired-absent reservations, released-later deletions) and are never silently lowered. Physical disk monitoring, filesystem overhead, category retention, tenant-wide holds, offboarding/erasure, backup expiry, restored-backup enforcement and provider/derivative erasure remain open. No customer-data, public-deployment or S3 gate changes.
